# 정적 hover 대안 — 인터랙션 없이 정보 밀도 표현하기

Bokeh HoverTool(`04-bokeh.md` A8재해석)이 "마우스를 올린 순간 보여주는 것"을 markdown에 박히는 정적 SVG에서 "처음부터 보이거나, 필요할 때 찾아볼 수 있게" 어떻게 재현할지 정리한다.

## Bokeh tooltip이 실제로 보여주는 것

`tooltips=[("label", "@field{format}"), ...]` 하나는 세 요소의 결합이다: **필드 선택**(어떤 값을) + **포맷 스펙**(어떻게 표시할지) + **표시 형태**(라벨-값 쌍 나열 vs 자유형 HTML). 이 구조는 인터랙션과 무관하게 "값을 사람이 읽기 좋게 포맷한다"는 범용 문제이므로, 그대로 정적 라벨 API의 스펙으로 이식한다.

## 4가지 정적 대안과 트레이드오프

### (a) 인라인 데이터 라벨 — 포인트 옆에 상시 표시
```python
sp.scatter(data, x="date", y="close", label="@close{$0.00}")
```
장점: hover 없이 값이 즉시 보임, 가장 직관적. **트레이드오프**: 포인트 수가 수십 개를 넘으면 텍스트 겹침이 즉시 발생 — Bokeh는 이 문제를 `limit`/`sort_by`/`filters`(런타임 필터링)로 풀었지만, 정적 렌더링은 그 시점 선택권이 없으므로 **사전 라벨 배치 알고리즘(force-directed 또는 leader-line) 또는 표시 개수 상한이 필수**. HTML 템플릿급 풍부한 콘텐츠(이미지, 다단 grid)는 인라인 공간에 안 들어가므로 텍스트 1~2줄로 축약해야 한다.

### (b) 사이드/하단 패널 — 극값·이상치만 선별
```python
sp.scatter(data, x="date", y="close", annotate="top3,bottom3")
```
Bokeh의 `sort_by`+`limit`이 하던 역할을 저자가 미리 결정한 정적 뷰로 대체. 장점: 카드형 콘텐츠(이미지 포함)도 패널에서는 공간 제약이 적어 원본 hover에 가장 가깝게 복원 가능. **트레이드오프**: "이 점이 왜 선택됐는지" 번호-매핑을 시각적으로 따라가야 해 즉각성이 떨어지고, 어떤 점을 뽑을지 저자의 판단(휴리스틱)이 개입되어 "아무 점이나 볼 수 있다"는 완전성을 잃는다.

### (c) SVG `<title>`/`<desc>` — 접근성 보너스일 뿐, hover 대체 아님
Phase 1 조사(`01-pygal.md`/`02-matplotlib.md`/`03-seaborn.md` A9)에서 세 라이브러리 모두 이 속성이 전무하다는 걸 확인했으므로 기본 포함(`14-scope-recommendation.md`의 필수 항목과 동일). **다만 명확히 해야 한다: 이건 스크린리더용이지, markdown `<img>` 임베드에서는 이마저 DOM 진입이 안 되어 데스크톱 사용자에게는 전혀 작동하지 않는다.** standalone으로 SVG를 직접 열었을 때(v2.0 시나리오)만 브라우저 네이티브 툴팁으로 살아난다.

### (d) 각주형 데이터 테이블 — 차트 아래 원본 값 병기
```python
chart.render_to_file("chart.md", table=True)  # pygal render_table 패턴 계승
```
Bokeh tooltip의 "라벨-값 쌍" 구조가 테이블의 "컬럼 헤더-셀" 구조와 정확히 대응되므로 **정보 손실이 가장 적다**. 이미지/HTML 임베드는 축약 표현(썸네일, 요약 텍스트)이 필요. **트레이드오프**: 차트-포인트와 표-행의 대응 관계를 사용자가 찾아야 하므로 (b)의 번호 매핑과 결합하면 자연스럽다. 포인트 수백~수천이면 표 자체도 감당 불가 — 상위 N개 요약 + "전체는 별도 CSV 링크"가 현실적.

## 핵심 설계 결정: 단일 스펙, 다중 출력

Bokeh의 `tooltips` 리스트를 **하나의 `label_spec`**으로 정의하고, 이를 (a) 인라인 라벨, (b) 사이드 패널, (d) 각주 테이블 세 렌더러에 동일하게 먹인다 — 콘텐츠를 세 번 따로 정의하지 않는다.

```python
spec = [("날짜", "@date{%Y-%m-%d}"), ("종가", "@close{$0.00}"), ("거래량", "@volume{0.0a}")]
sp.scatter(data, x="date", y="close", info=spec, info_display="table")  # or "inline" / "panel"
```

포맷 스킴은 Bokeh를 따라 3종으로 분리한다: **numeral**(`{0,0.000}`, 통화/천단위/축약), **datetime**(`{%Y-%m-%d}`), **printf**(`{%.2f}`) — 값의 dtype마다 다른 서식 언어를 쓰는 게 자연스럽다는 게 Bokeh가 이미 검증한 결론이다.

## `{safe}`(HTML 이스케이프 해제)는 채택하지 않는다

Bokeh조차 이 옵션에 "sanitize untrusted input" 경고를 명시적으로 붙인다. 산출물이 markdown/README에 그대로 박히는 이 프로젝트 특성상, 원시 HTML 삽입 경로 자체를 열지 않는 편이 안전하다 — SVG는 태생적으로 `<foreignObject>` 없이는 HTML을 못 담으므로, 이 경로를 굳이 만들지 않는 것이 기본값이다.

## MVP 스코프 판정

| 기능 | 판정 | 근거 |
|---|---|---|
| `label_spec`(필드+포맷 단일 스펙) | 필수 | (a)/(b)/(d) 세 렌더러의 공통 기반, 구현 비용 대비 재사용성 높음 |
| numeral/datetime/printf 3종 포맷 스킴 | 필수 | Bokeh가 검증한 최소 분류 |
| (d) 각주형 데이터 테이블 렌더러 | 필수 | pygal `render_table` 선례 있음, 정보 손실 최소 |
| (c) `<title>`/`<desc>` | 필수 | Phase 1에서 이미 필수로 결정됨(접근성), hover 대체 목적 아님을 문서에 명시 |
| (a) 인라인 라벨 + 겹침 회피 알고리즘 | 2차 | 라벨 오토플레이스먼트는 구현 비용이 큼 — 겹침 회피 없이 "라벨 밀도 낮을 때만 자동 켜짐"으로 좁혀 시작 |
| (b) 극값/이상치 자동 선별 패널 | 2차 | 선별 휴리스틱(top-N, IQR outlier) 설계가 필요 |
| `{safe}`류 원시 HTML 삽입 | 제외 | 보안·아키텍처 이유로 채택 안 함 |
